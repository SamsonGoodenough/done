PHASE 4

Episode & season logging (TV)

4 / 4

Complete

Merged to main via PR #3 on 2026-11-06. Design locked in via a grilling + domain-modeling session (new GLOSSARY.md terms Episode and Logging Target; see ADR 0004 for the sync-architecture trade-off).

  • ✓episodes migration, synced from TMDB per showMerged to main. Sync is lazy: the first GET /api/media-items/{id}/episodes call for a show fetches every season (a new SupportsEpisodeSync contract on TmdbClient, since only TV needs this), persisting season-by-season so a mid-sync failure keeps whatever already succeeded; this also self-backfills shows cataloged before this phase existed. A still-airing show gets re-checked for a newly-appeared season on every subsequent read, with the refreshed status written back as a side effect; the check stops permanently once a show's status goes terminal (Ended/Canceled). A manually-cataloged show (no external_id) is left alone entirely, returning whatever's already stored locally.
  • ✓Extend log_entries with nullable episode_id and season_number columnsMerged to main.
  • ✓Application-layer validation: episode_id/season_number mutual exclusivity, episode belongs to the showMerged to main. Also rejects episode/season granularity on any non-tv_show media item, and a season can't be logged until it's actually been synced.
  • ✓Rewatch detection scoped per target, not just per showMerged to main. LogEntryRecorder scopes by exact Logging Target (same episode_id, or same season_number, or both null), so a whole-show log entry is never a rewatch relative to a season- or episode-level entry made under it.

A code review (high effort) before merge found and fixed one real bug: EpisodeSyncer::episodesFor() called TmdbClient::showSummary() unconditionally, which crashed with a TypeError for any manually-cataloged (source = manual) TV show, since external_id is always null for those, reproduced live via tinker. Fixed with an early return for external_id === null, plus a regression test. The same review also flagged this phase's new files for using em dashes against this repo's style convention (CLAUDE.md); fixed throughout the new/changed code and this phase's own doc prose. Unlike Phase 2's pervasive-em-dash finding, this one was small enough to fix in the same pass rather than deferred. 21 new/updated backend tests, 110 total passing at merge, Pint clean.

Friends & profile visibility

6 / 6

Complete

Merged to main via PR #4 on 2026-11-07. Design locked in via a grilling + domain-modeling session (new GLOSSARY.md terms Friendship, Friend Request, Unfriending, Profile Visibility, Activity Feed, New from Friends, and a clarified Tag Friends; see ADR 0005 for why both activity surfaces include unrated log entries and why New from Friends needs its own per-friend query rather than a filtered view of the feed). A code review (high effort) found and fixed two real issues before merge: a genuine crossing-request race (closed with a Postgres advisory lock scoped to the user pair) and an N+1 in New from Friends (rewritten as a single query using a ROW_NUMBER() window function, portable across Postgres and sqlite, which also sidesteps a correctness bug in the naive MAX()-plus-self-join alternative).

  • ✓friendships migration and model; send/accept/decline request endpointsMerged to main. Directional requester/addressee rows (FriendshipManager); a crossing request auto-accepts instead of creating a second row; declining soft-deletes immediately so a fresh request works right away with no cooldown; either party can unfriend an accepted friendship.
  • ✓users.profile_visibility settings endpointMerged to main. The column already existed from Phase 1; PATCH /api/profile/visibility is the new part this phase adds.
  • ✓Member search/discovery endpointMerged to main. GET /api/members/search, unrestricted by any member's Profile Visibility; each result carries the viewer's own relationship status (none/pending-sent/pending-received/friends).
  • ✓Visibility-aware profile endpoint (public vs. private vs. friends-only)Merged to main. GET /api/members/{user} always returns basic info; shelf/diary/friend-list attach only when UserPolicy::viewPrivateContent allows it; a private profile the viewer can't see still returns 200 with those keys simply absent, not a 403.
  • ✓Activity feed endpoint: friends' recent activity, with no-friends-yet fallbackMerged to main. GET /api/activity/feed shows every accepted friend's Log Entry regardless of rating/review, most-recently-created first; falls back to the viewer's own entries, same composition, with no friends yet.
  • ✓New from Friends endpointMerged to main; added to scope during this phase's grilling session, not in the original checklist. GET /api/activity/new-from-friends: one entry per friend, their single most recent Log Entry where they're the logger (never a tagged-only entry), sorted by recency, no staleness cutoff. A single query ranks every friend's entries with a ROW_NUMBER() window function and keeps the top-ranked row per friend, so the query count stays flat regardless of friend count.

A code review (high effort) before merge found and fixed two real issues: a genuine crossing-request race where two simultaneous opposite-direction requests could each read "no reverse row yet" and create two independent pending rows instead of one accepting the other (closed with a Postgres advisory lock scoped to the user pair, verified against real Postgres via tinker), and an N+1 in New from Friends (one query per friend), rewritten as a single query with a ROW_NUMBER() window function that also avoids a correctness bug in the naive MAX(created_at)-plus-self-join alternative (which can return two rows for a friend whose two entries share the exact same timestamp). 38 new backend tests, 148 total passing at merge, Pint clean.

PHASE 6

Comments & reactions

3 / 3

Complete

Merged to main via PR #5 on 2026-11-08. Design locked in via a grilling + domain-modeling session (new GLOSSARY.md terms Review, Comment, Reaction, Moderation; see ADR 0006 for why the Activity Feed, New from Friends, and item-detail diary endpoints were also touched this phase, ahead of Phase 9's frontend, to embed comment/reaction summaries).

  • ✓comments migration (self-referencing parent_comment_id, soft delete) and threaded endpointsMerged to main. GET/POST /api/log-entries/{logEntry}/comments, DELETE /api/comments/{comment}; a flat, created_at-ordered list with an id tiebreak (no pagination); a comment only accepts a parent_comment_id belonging to the same Log Entry (including a soft-deleted one, so replies to a deleted comment stay valid); deleting is always a soft-delete ("[deleted]" placeholder, replies preserved) and is available to the comment's own author, the review's author, or any Admin.
  • ✓reactions migration (fixed emoji enum) and endpointsMerged to main. Fixed six-value enum (thumbs_up, heart, laugh, wow, sad, fire); GET/POST /api/log-entries/{logEntry}/reactions (idempotent POST, full per-emoji/reactor breakdown + viewer's own reactions on this endpoint), DELETE /api/log-entries/{logEntry}/reactions/{emoji} (idempotent, removes only the caller's own).
  • ✓Spoiler-gating applied to comment visibility, matching the parent reviewMerged to main. No additional backend work needed: contains_spoilers already lives on the Log Entry and is already returned by LogEntryResource/ActivityEntryResource (Phase 4); the blur/reveal behavior itself is a frontend concern, tracked under Phase 9.

Both Comments and Reactions are gated to a Log Entry that actually has a Review (422 otherwise) and to whoever can already view that Review per the Phase 5 friend/visibility policy, reused unmodified. The Activity Feed, New from Friends, and item-detail diary endpoints were extended with comment_count (including soft-deleted comments) and a condensed reaction_summary (total count + the viewer's own reaction(s)) on each Log Entry's serialization, to avoid a repeat of the N+1 pattern already caught in code review twice (Phases 2 and 5) — see ADR 0006.

A code review (high effort) before merge found and fixed two real issues: the visibility check for POST .../comments and POST .../reactions ran in the controller body, after the Form Request's own validation (including the review-must-be-non-null check) had already executed, so a stranger forbidden from viewing a private profile's entry got a 422 revealing the entry's existence and review state before ever being authorized to know either, fixed by moving the visibility check into StoreCommentRequest/StoreReactionRequest's own authorize(), which Laravel always runs before validation. And the comment thread listing was ordered by created_at alone, with no tiebreaker for two comments posted in the same instant, inconsistent with the explicit id tiebreak this same phase's ActivityController::newFromFriends uses for exactly this reason, fixed by adding the same tiebreaker. 34 new backend tests added, 185 total passing at merge, Pint clean.

Branch feature/phase7-notifications off main, all checklist work below done on the branch and passing (208 backend tests, Pint clean) but not yet merged, no PR opened yet. Design locked in via a grilling + domain-modeling session (new GLOSSARY.md term Notification; see ADR 0007 for why the six trigger points fire domain events into queued listeners rather than calling a notification service directly).

  • notifications migration and modelDone on the branch, not yet merged. user_id, type (NotificationType backed enum: tagged, friend_request, friend_accepted, comment_on_review, comment_reply, reaction), data (JSON payload per type), read_at, full timestamps + soft delete.
  • Notification-creating side effects: tagging, friend request/accept, comments/replies, reactionsDone on the branch, not yet merged. Tagging (UserTagged, from LogEntryRecorder), friend request/accept (FriendRequestSent/FriendRequestAccepted, from FriendshipManager and FriendshipController::accept), comments/replies (CommentPosted, from CommentManager), reactions (ReactionAdded, from ReactionManager, only on an actual create). Each event has one ShouldQueueAfterCommit listener that creates the Notification row, always self-suppressed. A top-level comment notifies only the review's owner; a reply at any depth notifies only its immediate parent comment's author, never both for the same comment.
  • Unread count + mark-read endpointsDone on the branch, not yet merged. GET /api/notifications, GET /api/notifications/unread-count, PATCH /api/notifications/{notification}/read (idempotent, ownership-gated), PATCH /api/notifications/read-all. No user-facing "clear"/dismiss action in v1 — deleted_at is reserved for a future system-side retraction, not exercised yet since there's no existing way to undo any of the six trigger events.

Testing while building this phase found and fixed one real pre-existing bug: Comment::parent() didn't include soft-deleted comments, so a reply notification for a reply-to-a-deleted-comment (explicitly allowed by StoreCommentRequest) crashed on a null parent, fixed by adding withTrashed() to that relation.

A code review (high effort) before merge found and fixed three more real issues: CreateCommentNotification and CreateReactionNotification both dereferenced logEntry->userMedia->user_id without accounting for the Shelf Entry being soft-deleted independently of its Log Entry, a real production race since these are queued listeners that can run well after the triggering request, fixed with withTrashed() on that relation lookup in both listeners, with regression tests driving the listeners directly to simulate the delayed-queue timing a synchronous test run can't otherwise reproduce. NotificationController reused MemberResource for a notification's actor without ever setting the relationship_status attribute that resource expects the controller to compute, so every actor silently reported relationship_status: null; fixed by not reusing that resource for this narrower purpose. LogEntryRecorder reloaded the participants relation twice on every tagged log entry; fixed to reload once. 23 new backend tests added in total, 208 total passing, Pint clean.
