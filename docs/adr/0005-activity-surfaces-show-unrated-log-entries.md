# Activity Feed and New from Friends surface every Log Entry, not just rated/reviewed ones

**Status:** accepted

The obvious design for a social activity surface is to show only Log Entries with a rating or review attached, treating a bare "watched, no rating" entry as too thin to be worth surfacing. We rejected that: some friends in the target user base consistently log without rating, and seeing that they watched something is itself the value, not a side effect of them also reviewing it. Both the Activity Feed and New from Friends show every Log Entry regardless of rating/review, with no filtering by content richness.

This has one accepted cost: a show logged episode-by-episode posts one feed item per entry, with no rollup or burst-grouping. That's deliberately deferred rather than designed around, since nothing has demonstrated it's actually a problem yet.

New from Friends (one entry per friend: their single most recent Log Entry, sorted by recency, no staleness cutoff) is a separate query from the Activity Feed rather than a client-side filter over it. The feed isn't paginated today, but it will need to be eventually (nothing bounds how much history it returns as friends keep logging), and deriving "latest per friend" from a paginated feed would silently drop a friend who hasn't logged recently once their entry falls off the loaded page, which defeats the section's purpose: showing every friend's latest, however old. It only counts entries where the friend is the logger (`log_entries.user_id`), never one where they're tagged as a participant, consistent with Tag Friends being purely informational and never surfacing on the tagged user's own activity.

That "separate query" is a single query, not one per friend. The per-friend ranking is done with a `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC, id DESC)` window function, filtered down to `rn = 1`, which is standard SQL supported by both Postgres (production) and sqlite (tests), so this stays portable without resorting to Postgres-only syntax like `DISTINCT ON`. This app is sized for well under 50 users, so an N+1 (one small indexed query per friend) would have been fine performance-wise at this scale, but the single-query form was worth the small amount of extra complexity for two reasons: it doesn't degrade as a user's friend count grows, and the naive one-query alternative (`MAX(created_at)` grouped by friend, then joined back to pull the full row) has a real correctness bug, that join matches on the timestamp value rather than a unique row, so two entries sharing the exact same `created_at` would both come back instead of exactly one. The window function's `id DESC` tiebreaker avoids that case entirely.
