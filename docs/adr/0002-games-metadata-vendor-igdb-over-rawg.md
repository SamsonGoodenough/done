# Games metadata vendor: IGDB over RAWG

**Status:** accepted

`07-external-integrations.md` originally picked RAWG for games metadata over IGDB, specifically for RAWG's simpler single-API-key auth versus IGDB's OAuth2 client-credentials flow via a Twitch Developer account. That recommendation is superseded: RAWG turned out to have undocumented multi-day outages with no status page and no public incident communication (a documented full-day blackout on 2024-05-05, and all three of its surfaces — site, API, and docs — returned Cloudflare 522 simultaneously during the research that prompted this change). GameVault, a comparable self-hosted game-library project, independently hit the same wall and migrated to IGDB for the same reason.

IGDB was chosen as the replacement: it's the only alternative where all five fields this project needs (title, release date, cover, platforms, developer) were confirmed directly from current official docs, the only one with an explicit documented rate limit (4 req/s, 8 concurrent), free for non-commercial use, and its Twitch OAuth dependency has a real public status page to check against. The extra auth ceremony (Twitch Developer account, 2FA, client-credentials token fetch and cache) is accepted as a one-time implementation cost rather than a reason to stay with RAWG, because [ADR 0001](0001-media-source-integration-architecture.md) already isolates vendor specifics behind a swappable `MediaSource` client binding — this is exactly the swap that architecture was built to absorb. The `games_api` value stored in `media_items.source` is unchanged.

Full research and citations: [`docs/research/games-api-alternatives-to-rawg.md`](../research/games-api-alternatives-to-rawg.md). Giant Bomb was the runner-up (RAWG-simple auth, flattest schema) but wasn't picked because its rate limit and current live reachability couldn't be confirmed from primary sources in that research; worth revisiting if IGDB proves difficult in practice.
